二、從新聞蒐集到報告輸出的完整資料流程
--------------------------------------------------------------------------------

[1] 來源擷取階段
   ├─ fetch_news*.py          -> Google News RSS 搜尋（中/英文）
   ├─ fetch_rss.py / fetch_rss_direct.py -> 直接 RSS 訂閱
   ├─ fetch_google_news.py    -> Google News 搜索 + 去重
   ├─ fetch_key_articles.py   -> 固定關鍵文章 URL（硬編碼）
   └─ fetch_articles.py       -> 嘗試解析 Google News 文章 ID

[2] 內容擷取
   └─ jina.ai (r.jina.ai/http://...) -> 將記事頁面轉成純文字
     ※ 目前拿到的多為「首頁靜態內容」或「轉譯過的摘要」
     ※ 無法可靠抵達單篇原文（見 V 檢測）

[3] 篩選 / 去重
   ├─ 根據 URL / 標題 / 來源白名單篩選
   ├─ 按標題作空間去重（簡單字串去重）
   └─ 僅「日期」級的日誌級動態

[4] 生成（關鍵缺口）
   ├─ generate_vp_report6.py / generate_vp_report6_v7.py
   ├─ generate_1105_report_v2.py / generate_vp_report7.py
   ├─ generate_news_v3.py / generate_single_version_v3.py
   ├─ 三家公司版：generate_multi_version_v3.py
   └─ 輸出：.txt（含固定模板 + 來源清單）

[5] 清洗 / 消毒
   ├─ sanitizer_banned_words() -> 移除「投資、股價、目標價、買超...」等投資溯源詞
   └─ 保留「來源與標題」段落（作為來源註記）
   └─ MP3 重新生成（edge-tts zh-CN-XiaoxiaoNeural -10%）

[6] 預測（Validation Gate）
   ├─ 日期、UTF-8、字數（CJK 1200–1800）
   ├─ 來源白名單 / Tier-1 國際門檻 / 來源占比
   ├─ 禁止詞檢查
   ├─ 關鍵實體核對（員工姓名邏輯）
   └─ 文章體裁檢查（禁止條列、句子平均長度）

[7] 儲存 / 推播
   ├─ Supabase Storage「news」空間（TXT + MP3）
   ├─ 產生 CDN URL（約 24 小時有效）
   └─ LINE 07:00 / 07:30 推播（推播標題固定）

[8] 發送
   ├─ LINE push（推播標題：台積電，日月光，聯發科 每日新聞稿）
   └─ Discord 備份上傳

四、最可能造成「內容重複」及「錯誤」的前三項原因
--------------------------------------------------------------------------------

原因 1：生成是在「固定模板」上跑，而非用 LLM 生成新內容
-----------------------------------------------------------
generate_vp_report6.py、generate_vp_report6_v7.py、generate_1105_report_v2.py、
generate_vp_report7.py、generate_news_v3.py、generate_single_version_v3.py、
generate_multi_version_v3.py 這些腳本，它們的文章本體是：

    single_text = f"""2026年{FILE_DATE[4:6]}月{FILE_DATE[6:8]}日 台積電深度產業新聞稿
    ...

這是同一個金字塔式段落逐段複製，僅替換日期、來源清單、口號。跨日期的文章幾乎是
同一段骨架 + 不同標題 + 不同尾段。
導致：
- 不同日期文章重複率極高；
- 缺乏對「當日事件」的真實分析；
- 產生的文章失去「當日新聞」的動態感；
- 給 AI 傳入的是「今天有哪些新聞」的脈絡，但生成時並不是依據它。

原因 2：沒有持久快取 / 去重 / 來源資料庫，導致每次輪詢都重新生成、且常使用同一批新聞
-----------------------------------------------------------------------------------------
- 快取：/home/ase/.hermes/cron/ 目錄有歷史存檔，但沒有命中快取的機制。
       每次 cron 重新發送請求、重新抓取、重新生成。
- 去重：只在有限的 fetch_*.py 腳本中依標題做「小寫去重」，
       並沒有一個持久化的去重索引。
- 因此：
  - 當日新聞集中在少數來源；
  - 同一主題在不同日期反覆出現；
  - 模板裡的新聞標題、來源清單幾乎不變；
  - 不同日期的「產業概論」段落高度相似。

原因 3：文章生成與來源內容未做「事件日期同步」与「來源指向」，驗證也只是事後檢查
---------------------------------------------------------------------------------------
- 生成的文章中「來源與標題」是靜態寫死的，來源 URL 為首頁
  （例如 https://www.reuters.com），不是實際文章連結。
- 文章內的分析是模板化，無法根據那天抓取到的實際新聞內容做事實核對。
- daily_news_cron_v3.py 的 validate_version() 為：
  - 編碼、字數、禁止詞、員工名稱邏輯；
  - 不檢查「文章內容是否真的描述了當日事件」；
  - 不檢查「來源標題與正文是否一致」；
  - 不檢查「文中任何事實是否在後續當日尚未披露」。
- 因此錯誤信息會在多個日期連續出現（偶發性），因為正文是人為寫的，不是驗證過的。

--------------------------------------------------------------------------------
六、總結
--------------------------------------------------------------------------------

目前這個 Hermes News Agent 的「每日新聞生成流程」可以概括為：

    Google News RSS / RSS 訂閱 -> 抓取 -> 簡單去重 -> 寫入硬編碼模板
       -> 靜態生成 .txt
       -> 消毒、生成 MP3
       -> 字數 / 來源門檻 / 禁止詞檢查
       -> 上傳 Supabase -> LINE 推播

最大問題不在於「沒有工具」或「配置錯誤」，而是在於：

1. 生成腳本是靜態模板，並沒有真正地「讀取今日新聞」->「產生當日文章」；
2. 新聞抓取階段只取得「標題 / 來源 / 首頁 URL」，沒有持久快取，導致重複與
   內容過時；
3. 文章內容與當日事實缺乏雙向鎖定，產生大量重複段落與偶發性錯誤；
4. 來源 URL 為首頁，無法追溯原文。

| 診斷問題 | 根本原因 | 修正優先文件 |
| ---------------------------------------- | ---------------------------------------- | --------------------------------------------------------- |
| 每日文章高度重複 | 硬編碼模板，跨日期複製 | generate_vp_report6.py、generate_vp_report6_v7.py、generate_1105_report_v2.py |
| 文章沒有充分分析當日事件 | 模板內容不是來自當日新聞，而是固定「產業概論」 | fetch_google_news.py、generate_vp_report6.py |
| 部分錯誤連續出現在不同日期 | 沒有事前事實鎖定，事後驗證薄弱 | daily_news_cron_v3.py、generate_vp_report6.py |
| 文章偏產業概論 | 生成器只靠模板，不依賴今日新聞 | generate_vp_report6.py、daily_news_cron_v3.py |
| 來源只顯示首頁，無法追溯原文 | 來源清單硬編碼，URL 為首頁 | generate_vp_report6_v7.py、daily_news_cron_v3.py（validate_version） |
